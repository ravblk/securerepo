Понял вас. Значит, 50 чанков — это **не жесткий лимит обрезки**, а **средний ожидаемый объем** одного репозитория, от которого отталкивается расчет пропускной способности системы (5 аудитов × в среднем 50 чанков = 250 чанков в обработке). 

Я убрал логику принудительной остановки и перевел это в плоскость расчета нагрузки и SLA. Если репозиторий окажется больше, система не должна «падать» или обрезать аудит, но расчет параллельности идет на среднюю величину.

## 2. Бизнес-правила (BR)

Жесткие ограничения логики, которые система проверяет до или во время выполнения функций.

- **BR-01 [Окно аудита и объем]:** Аудит выполняется строго в рамках одного репозитория за одну сессию. Средний ожидаемый объем одного репозитория составляет **50 чанков**. Система должна обрабатывать весь объем переданного кода без принудительной обрезки, однако расчет пропускной способности и параллелизма опирается на среднюю величину.
- **BR-02 [Air-gapped]:** Система не имеет доступа к внешним LLM API (OpenAI, Anthropic). Весь инференс — локальный внутри периметра клиента.
- **BR-03 [Детерминированность]:** LLM запрещено использовать внутренние знания. Анализ опирается ТОЛЬКО на контекст из RAG. Каждое нарушение должно ссылаться на конкретный пункт регламента.
- **BR-04 [Гибридность правил]:** Аудит выполняется на пересечении внутренних политик (Internal Rules Ingestion) и общих практик (OWASP/CWE).
- **BR-05 [Параллелизм]:** Система поддерживает одновременный аудит до 5 репозиториев (5 параллельных сессий).

## 4. Нефункциональные требования (NFR)

1. **Производительность:**
   - Платформа должна обеспечивать одновременный аудит 5 репозиториев.
   - Средний ожидаемый объем одного репозитория: **50 чанков** (до 250 чанков в одновременной обработке/очереди).
   - Calls Per Second (CPS): до 5 (по 1 на каждый активный поток аудита).
   - Задержка LLM (время отклика): < 5000 мс на чанк.

2. **Доступность (SLA):** 99.9% времени работы (допускается не более 43.8 минут простоя в месяц).

3. **Безопасность:**
   - Все HTTP-запросы (API, Webhooks) шифруются TLS 1.2+.
   - Air-gapped: нет внешних API-вызовов.
   - Локальное хранение данных (без облачных сервисов).

4. **Масштабируемость:**
   - Kafka-based оркестрация для горизонтального масштабирования (управление 5 параллельными консьюмерами).
   - Qdrant — до 1M векторов в коллекции.

5. **Мониторинг:**
   - Логирование в PostgreSQL (аудит-логи: кто, когда, что запустил).
   - Метрики: количество обработанных чанков, средний размер репозитория (в чанках), ошибки, время выполнения, количество активных параллельных сессий.

## 5. Архитектурные риски и допущения

1. **Риск парсинга:** Tree-sitter может некорректно обработать сложные файлы (многострочные строки, макросы). Решение: добавить fallback на регулярные выражения для известных паттернов.
2. **Риск RAG-качества:** Если эмбеддинги не находят релевантные правила — LLM не сможет выявить уязвимость. Решение: в MVP ограничить политики до 50 правил, протестировать recall.
3. **Риск LLM-галлюцинаций:** При отсутствии контекста LLM может выдумать уязвимость. Решение: промпт с явным запретом на использование внутренних знаний; если релевантные правила не найдены — возврат «не применимо».
4. **Риск превышения среднего объема:** Если репозитории систематически превышают средние 50 чанков, общая пропускная способность системы снижается, накапливается очередь. Решение: жесткое ограничение concurrency в vLLM на уровне 5, очередь Kafka сглаживает пик, метрики мониторинга сигнализируют о росте среднего размера.
5. **Допущения:**
   - Репозиторий доступен любой по токену или без.
   - Internal Rules Ingestion — загрузка политик (MVP).
